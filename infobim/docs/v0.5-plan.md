# InfoBIM v0.5 — Rebuild Plan

Updated: 2026-08-12

## Objective

Rebuild InfoBIM against the current OntoBDC stack and produce a coherent, demonstrable v0.5 for presentation on 2026-08-13.

The goal is **not** to repair or modernize v0.4 in place. v0.4 is frozen as historical implementation evidence.

## Reset strategy

- Branch `v0.5` starts from `v0.4` so all history remains traceable.
- The complete previous implementation is preserved under `src/old/`.
- A new active package begins under `src/infobim/`.
- Nothing is copied back automatically.
- Recovery from `src/old` is selective and responsibility-driven.

## Architectural rule

Before recovering any old implementation, classify it as one of:

1. **OntoBDC responsibility** — do not reimplement in InfoBIM.
2. **ontobdc-view responsibility** — do not reimplement in InfoBIM.
3. **InfoBIM/BIM responsibility** — cherry-pick or reimplement in the new package.
4. **Obsolete** — leave in `src/old`.

### OntoBDC owns

- semantic runtime and state/capability execution;
- containers and datasets;
- generic entity handling;
- WorkStream semantics and generic behavior;
- generic resource relationships;
- generic annotation semantics/runtime;
- generic presentation contracts and publication lifecycle.

### ontobdc-view owns

- reusable presentation components;
- Tiles and generic entity pages;
- browser-side presentation assets that are not BIM-specific.

### InfoBIM owns

- BIM/OpenBIM domain profiles;
- IFC/BIM-specific resource semantics and resolution;
- BIM-specific display/representation policy when genuinely domain-specific;
- domain-specific adapters/capabilities that cannot be expressed generically in OntoBDC;
- InfoBIM-specific configuration, labels and branding where appropriate.

## Baseline dependencies

Initial v0.5 package baseline:

- `ontobdc>=0.14.0`
- `ontobdc-view>=0.1.0`

No v0.4 dependency is retained merely because old code imported it. Dependencies return only when recovered v0.5 code demonstrates that they are required.

## Execution plan for 2026-08-12

### 1. Reset repository — DONE

- [x] create `v0.5` from `v0.4`;
- [x] preserve old implementation as `src/old`;
- [x] create clean `src/infobim`;
- [x] set package version to `0.5.0`;
- [x] reset package dependencies to the current OntoBDC stack;
- [x] rewrite README around the new architectural boundary.

### 2. Establish the minimum InfoBIM domain shell

- [ ] inspect current OntoBDC/OntoBDC View public contracts;
- [ ] define the thinnest valid InfoBIM package and CLI entry point, if a separate CLI is still justified;
- [ ] restore only domain configuration required to identify an InfoBIM project/container;
- [ ] ensure clean installation/import from an empty environment.

### 3. Recover the demonstration path selectively

For each required behavior, inspect `src/old` first but prefer current OntoBDC APIs.

- [ ] project/container entry point;
- [ ] InfoBIM domain profile;
- [ ] WorkStream usage through current OntoBDC contracts;
- [ ] BIM-specific resource categorization/resolution only where OntoBDC is intentionally generic;
- [ ] IFC/BIM-specific preview representation behavior if required for the demo;
- [ ] InfoBIM labels/theme/branding only where not already declarative in the presentation stack.

### 4. Demonstration acceptance path

The version is demonstrable when one clean project can execute this path without manual code edits:

1. install the current packages;
2. initialize/open an InfoBIM project/container;
3. expose at least one WorkStream;
4. open its current OntoBDC entity page;
5. browse project resources;
6. preview a supported resource;
7. relate/unrelate that resource to a WorkStream dimension;
8. create and persist a supported annotation;
9. close/reopen and verify persistence.

### 5. Stabilize only blockers

Fix before the presentation only defects that:

- break installation;
- prevent project/container creation/opening;
- prevent the WorkStream page from opening;
- prevent resource preview/relationship;
- corrupt or lose persisted data;
- produce a visibly broken demonstration path.

Everything else becomes post-demo backlog.

## Explicit non-goals for tonight

- restoring every v0.4 feature;
- recreating code already generalized into OntoBDC;
- restoring all annotation categories/tools merely because old code had them;
- redesigning OntoBDC architecture;
- polishing non-blocking UX;
- recovering historical compatibility layers or aliases;
- broadening the demo beyond the single verified happy path.

## Historical planning note

The previous annotation/refactoring plan targeted OntoBDC `v0.12` and InfoBIM `v0.4`. It remains useful as historical evidence about architectural intent, especially the rule that WorkStream and generic annotation behavior belong to OntoBDC, but its version-specific implementation steps are superseded by this v0.5 rebuild plan.

## Stop condition

Once the acceptance path works from a clean environment, stop feature work for the night, record known limitations, and preserve a reproducible demo state for 2026-08-13.
